# AOS-SPEC-004 — CLI

**Status:** Accepted
**Authors:** AOS project
**Created:** 2026-07-26
**Updated:** 2026-07-26
**Depends on:** AOS-SPEC-002 — Repository; AOS-SPEC-003 — Protocol
**Supersedes:** None

## Purpose

This specification defines the stable command-line interface for read-only AOS
project intelligence and safe repository adoption. It maps the Information
Model, Repository, and Protocol contracts into user-facing commands without
implementing a CLI or selecting a programming language.

## Motivation

AOS needs a small, predictable entry point before it can become an executable
product. The CLI must make inspection and validation easy while ensuring that
initialization is plan-first, explicit, bounded, and auditable.

This specification advances:

- VISION G1 — Repository-native project intelligence.
- VISION G2 — Explicit and attributable truth.
- VISION G4 — Human-governed automation.
- VISION G6 — Open and extensible interoperability.

It is constrained by PRINCIPLES P1, P2, P5, P7, P8, P9, P10, and P12.

## Scope

This specification defines:

- command names and required behavior;
- root selection and common options;
- human and machine-readable output semantics;
- stable exit categories;
- read-only guarantees;
- plan-first `aos init` behavior;
- error, conflict, unsupported, and unknown result handling;
- output safety and audit references; and
- conformance cases for future CLI implementations.

## Non-goals

This specification does not define:

- a shell, terminal, or operating-system installation mechanism;
- a programming language, parser library, or process supervisor;
- a graphical interface;
- Runtime adapter or AI provider APIs;
- a physical `.aos/` layout;
- a universal configuration file;
- interactive prompt wording; or
- bypass flags such as `--force` or `--unsafe`.

## Terminology

### Command

A named CLI operation with defined inputs, output, side effects, and exit
categories.

### Human output

Readable output intended for a person. It may include formatting but must
preserve the same semantic result as machine output.

### Machine output

Structured output intended for scripts and tools. Its logical fields and
success/error semantics are stable even when human wording changes.

### Diagnostic

An attributable observation about repository scope, validity, compatibility,
ownership, policy, or operation result.

### Plan result

A non-mutating description of proposed changes and preconditions.

## Normative requirements

### CLI identity and invocation

**CLI-001.** The executable name **MUST** be `aos`.

**CLI-002.** A command **MUST** return a stable exit category and a semantic
result. Human wording **MUST NOT** be the only machine integration contract.

**CLI-003.** A command **MUST** operate on one resolved Repository Root and
**MUST** use the discovery and boundary rules in `AOS-SPEC-002`.

**CLI-004.** A command **MUST NOT** silently select an ancestor, sibling, or
external path when the Repository Root is absent or ambiguous.

**CLI-005.** The CLI **MUST** expose its product and contract version through
the `version` command or equivalent version query.

### Commands

**CLI-006.** `aos inspect [PATH]` **MUST** perform read-only Repository
inspection and report root, Repository status, Project identity when known,
compatibility, ownership findings, and evidence references.

**CLI-007.** `aos validate [PATH]` **MUST** perform read-only validation of
Information Objects, Repository state, references, compatibility, and required
contracts available to the selected scope.

**CLI-008.** `aos doctor [PATH]` **MUST** perform read-only diagnostics and
report actionable findings without applying repairs or changing project content.

**CLI-009.** `aos init [PATH]` **MUST** create or validate an Adoption Plan
without mutating the repository unless explicit apply intent and Governance
authority are both present.

**CLI-010.** `aos init --dry-run [PATH]` **MUST** produce the same class of
non-mutating plan result as the default `aos init` operation.

**CLI-011.** Repository mutation through the CLI **MUST** require an explicit
`--apply` intent. `--apply` **MUST NOT** bypass Repository ownership,
preconditions, Governance, or reconciliation requirements.

**CLI-012.** `--dry-run` and `--apply` **MUST** be mutually exclusive. The CLI
**MUST** reject unknown or contradictory command options before inspection or
mutation.

**CLI-013.** No command **MUST** mutate user-owned project content implicitly.
`inspect`, `validate`, and `doctor` **MUST** remain read-only under all options.

### Common options and root selection

**CLI-014.** Commands that accept `[PATH]` **MUST** treat it as an explicit
Repository Root candidate and apply canonicalization and boundary checks.

**CLI-015.** When `[PATH]` is omitted, the CLI **MUST** pass the caller context
to Repository discovery and report `ambiguous`, `unmanaged`, or a resolved root
explicitly.

**CLI-016.** `--format human` and `--format json` **MUST** select human and
machine output respectively. Human output is the default for an interactive
terminal.

**CLI-017.** `--format json` **MUST** emit one structured result on stdout and
**MUST NOT** mix progress text or human formatting into that result.

**CLI-018.** `--quiet` **MAY** suppress non-essential human output but **MUST
NOT** suppress a failure category, required diagnostic, or machine result.

**CLI-019.** A CLI implementation **MUST NOT** invent command-specific root,
ownership, compatibility, or authority rules that contradict the underlying
specifications.

### Output contract

**CLI-020.** Every command result **MUST** identify the command, CLI contract
version, outcome category, Repository Root when resolved, and evidence or
diagnostics.

**CLI-021.** Machine output **MUST** provide a stable logical envelope with:
`schema_version`, `command`, `outcome`, `repository`, `diagnostics`, and
`evidence` fields. Fields with no value **MUST** be represented explicitly as
empty or unknown according to the result.

**CLI-022.** A successful `init` plan **MUST** include the plan identity,
preconditions, ownership decisions, affected paths, authority requirement, and
recovery behavior.

**CLI-023.** An applied operation **MUST** include operation identity, result,
changed paths, verification, reconciliation status, and audit evidence.

**CLI-024.** Error output **MUST** identify a stable error category and
actionable diagnostic. It **MUST NOT** expose secrets or credentials.

**CLI-025.** Human and machine output **MUST** represent the same semantic
outcome, even if labels, ordering, or explanatory text differ.

### Exit categories

**CLI-026.** The CLI **MUST** use these stable exit categories:

| Category | Meaning |
| --- | --- |
| `0` | Requested operation completed successfully, including a valid read-only result or plan |
| `2` | Usage or option error |
| `3` | Repository root missing, inaccessible, or ambiguous |
| `4` | Validation or diagnostic findings prevent the requested result |
| `5` | Stale plan, ownership conflict, or concurrent change |
| `6` | Unsupported contract, Protocol, or Repository version |
| `7` | Authorization required, denied, expired, or scope-mismatched |
| `8` | Operation failed or has an unknown external result |
| `9` | Unexpected CLI failure; diagnostic evidence is required |

**CLI-027.** Exit category `0` **MUST NOT** be returned for an operation whose
result is unknown, unauthorized, incompatible, or only partially applied.

**CLI-028.** A command that reports findings without failing its requested
operation **MAY** use `0`, but the machine result **MUST** distinguish findings
from a clean result.

### Safety and lifecycle

**CLI-029.** The CLI **MUST** fail closed when root, ownership, authority,
compatibility, or external operation state is unknown.

**CLI-030.** The CLI **MUST** preserve the Repository plan/apply distinction
and **MUST** expose a way to inspect a plan before application.

**CLI-031.** `aos init --apply` **MUST** validate the plan snapshot immediately
before applying and **MUST** reject a stale plan.

**CLI-032.** After any partial or unknown apply result, the CLI **MUST** report
`degraded` or `unknown`, preserve operation evidence, and direct the caller to
reconciliation rather than retrying blindly.

**CLI-033.** The CLI **MUST NOT** provide an option that disables ownership,
authority, compatibility, or reconciliation checks.

### Security and compatibility

**CLI-034.** The CLI **MUST** use least-privilege capabilities and **MUST NOT**
echo secrets, credentials, or private keys in human or machine output.

**CLI-035.** A CLI that does not support a command, option, output schema, or
contract version **MUST** report an explicit unsupported result.

**CLI-036.** CLI output schema changes that break machine consumers **MUST**
use a new schema version and provide a migration or compatibility statement.

**CLI-037.** A CLI invocation **MUST** preserve the underlying Information
Object, Repository, and Protocol provenance and authority references.

### P4 Knowledge and Context commands

**CLI-038.** `aos knowledge [PATH]` and `aos state [PATH]` **MUST** query
stored Information Object revisions read-only unless an explicit record/apply
intent is supplied.

**CLI-039.** A Knowledge or State record request **MUST** include a stable
object ID, subject, content or observed value, source reference, and authority
reference. It **MUST** produce a reviewable plan without mutation unless
`--apply` is present.

**CLI-040.** P4 record creation **MUST** create proposed objects only.
`--apply` and `--authority` **MUST NOT** promote provider or caller content to
authoritative Project truth.

**CLI-041.** `aos context [PATH]` **MUST** perform provider-independent,
deterministic context selection and return selected records plus explicit
withholding reasons.

**CLI-042.** A context limit **MUST** be a positive integer. Records excluded
because of the limit **MUST** remain distinguishable from records excluded by
authority, lifecycle, freshness, or conflict.

**CLI-043.** P4 machine results **MUST** expose command-specific records or
context selection in a `data` field while preserving the common result
envelope.

**CLI-044.** `aos context` **MAY** accept `--profile full|compact`. `full`
**MUST** preserve the accepted record representation. `compact` **MUST** retain
the record kind, identity, revision, subject, source reference, authority,
lifecycle, applicable freshness, and content or observed value required by a
consumer to use the selected record safely.

**CLI-045.** `aos context` **MAY** accept `--budget-bytes N` with a positive
integer. The implementation **MUST** report the selected byte count and
withhold any otherwise eligible record that would exceed the budget with the
explicit reason `context_budget`. A budget **MUST NOT** cause a partial record
to be emitted.

## Interfaces and data flow

### Command map

| Command | Mutation | Primary contract |
| --- | --- | --- |
| `aos version` | No | CLI compatibility |
| `aos inspect` | No | Repository and Information Model |
| `aos validate` | No | Information Model, Repository, and Protocol |
| `aos doctor` | No | Repository diagnostics and governance |
| `aos init` | Plan by default; apply only with `--apply` | Repository and Governance |
| `aos knowledge` | Query by default; proposed record only with `--record --apply` | Information Model |
| `aos state` | Query by default; proposed observation only with `--record --apply` | Information Model |
| `aos context` | No | Information Model and Context selection |

### Result envelope

The logical machine result is:

```text
{
  schema_version,
  command,
  outcome,
  repository,
  diagnostics,
  evidence,
  data,
  plan,
  operation,
  error
}
```

The exact serialization is implementation-defined, but the semantic fields,
empty/unknown behavior, and exit categories are normative.

### Initialization flow

```text
aos init [PATH]
        |
        v
Repository discovery and inspection
        |
        v
Adoption Plan
        |
        +--> no --apply: print plan, no mutation
        |
        `--> --apply: authority + snapshot validation
                         |
                         v
                    bounded apply
                         |
                         v
                  verify/reconcile/result
```

## Lifecycle and state transitions

### Command invocation

```text
parse -> resolve root -> inspect -> validate -> report
                                     |
                                     `--> plan -> authorize -> apply -> verify
```

An invalid option stops at `parse`. An unresolved root stops at `resolve root`.
A read-only command stops after `report`. `init --apply` must pass every
intermediate stage.

### Init outcome

```text
plan-ready -> authorized -> applying -> verified
     |            |            |          |
     |            |            |          +--> success
     |            |            +------------> degraded/unknown
     |            +-------------------------> denied
     +--------------------------------------> conflict/invalid
```

## Failure behavior

| Condition | Required behavior |
| --- | --- |
| Unknown option or conflicting flags | Exit `2`; do not inspect or mutate |
| Missing or ambiguous root | Exit `3`; report explicit discovery result |
| Validation findings | Exit `4`; preserve diagnostics and evidence |
| Stale plan or ownership conflict | Exit `5`; require replanning |
| Unsupported contract | Exit `6`; do not guess behavior |
| Missing or invalid authority | Exit `7`; do not mutate |
| Failed or unknown apply | Exit `8`; preserve operation evidence and reconcile |
| Unexpected internal failure | Exit `9`; expose safe diagnostic only |
| Secret in output path | Redact or withhold; preserve reason and provenance |

## Security and governance

- CLI flags select intent; they do not replace Governance authority.
- Read-only commands remain safe even when called by an untrusted AI tool.
- `--apply` cannot bypass Repository ownership or Protocol constraints.
- Machine output is safe for automation and must not leak credentials.
- External operation uncertainty is surfaced, never hidden as success.
- The CLI must expose enough evidence to explain what it inspected and why it
  returned a result.

## Compatibility and migration

1. The CLI command contract, result schema, and exit categories are versioned.
2. A consumer that cannot support a command or schema version receives an
   explicit unsupported result.
3. Additive output fields may be introduced compatibly when unknown-field
   behavior is preserved.
4. Removing, renaming, or changing the meaning of a command, option, exit
   category, or required result field requires a new contract version.
5. A CLI upgrade must preserve Repository, Work, Protocol, provenance, and
   audit semantics.
