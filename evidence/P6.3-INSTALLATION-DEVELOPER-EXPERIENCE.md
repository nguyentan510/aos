# P6.3 Installation and Developer Experience

**Status:** ACTIVE — implementation and local Windows gates pass
**Date:** 2026-07-27
**Decision:** One-command setup and two checksum-verified installers are
implemented. P6.3 closes only after Linux hosted CI and published RC4 release
smokes pass. Production-like and production readiness remain unclaimed.

## Objective

Reduce first use from maintainer-only binary and manifest operations to:

```text
aos setup .
```

and a fresh-machine install plus project setup through one installer command.
The convenience layer must preserve Repository ownership, Governance authority,
extension digest, immutable revisions, auditability, and uninstall boundaries.

## Isolation from P6.2

The official P6.2 qualification subject is pinned outside this source
repository with binary, manifest, harness, commit, and SHA-256 records. A daily
automation appends at most one official sample per day. P6.3 changes therefore
cannot silently change the P6.2 subject.

This permits parallel progress under ADR-0011. It does not bypass or synthesize
the seven-day qualification gate.

## Implemented setup contract

```text
Inspect root
→ build plan
→ resolve local bootstrap Principal
→ one confirmation or --yes
→ transactional init
→ governed Generic enable
→ optional governed Rust enable
→ validate and write setup Audit
```

Verified behavior:

- folder must already exist;
- dry-run and machine output without confirmation are non-mutating;
- Generic is always selected;
- Rust is selected only for a regular root `Cargo.toml`;
- embedded manifests use the same P6 parser, digest, lifecycle, Governance, and
  Audit implementation as file-based enable;
- setup does not initialize Git, modify source, or create Knowledge/Work;
- repeated setup appends no new revision;
- unknown `.aos` remains untouched; and
- partial apply reports reconciliation instead of destructive rollback.

## Installer implementation

`install.ps1` supports Windows x86_64 and `install.sh` supports Linux x86_64
GNU. Both support online release resolution and offline archive/checksum
fixtures, staged verification, versioned installs, project setup composition,
and owned uninstall.

Windows default:

```text
%LOCALAPPDATA%\AOS\
|-- bin\aos.exe
|-- versions\<version>\...
`-- install.json
```

Linux default:

```text
${XDG_DATA_HOME:-$HOME/.local/share}/aos/
|-- versions/<version>/...
`-- install.json

$HOME/.local/bin/aos
```

The local Windows offline gate proves:

```text
archive + exact SHA-256
→ safe extraction
→ staged version smoke
→ fresh install
→ setup empty repository
→ doctor
→ repeated install
→ version switch and rollback
→ checksum tamper denial
→ archive traversal denial
→ modified-binary uninstall denial
→ owned uninstall
→ downstream .aos preserved

AOS_P6_3_INSTALL_WINDOWS_OK
AOS_P6_3_FRESH_PROJECT_SMOKE_OK
```

The equivalent Linux gate is
`scripts/run_p6_3_linux_installer_smoke.sh` and runs on hosted Ubuntu CI.

## Supply-chain and release binding

The RC4 workflow packages:

```text
aos-x86_64-pc-windows-msvc.zip
aos-x86_64-unknown-linux-gnu.tar.gz
install.ps1
install.sh
SHA256SUMS
GitHub build provenance attestations
```

After publishing, fresh Windows and Ubuntu jobs download the release assets,
run install plus setup, run doctor and the governed P6 extension smoke,
uninstall the distribution, and verify downstream `.aos` remains.
